# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Unity multiplayer game "Blood for Blood". Unity 6000.6.0f1 (6.6 LTS), Universal Render Pipeline, new Input System (exclusive — see Gotchas), Netcode for GameObjects for multiplayer.

Full design doc: `docs/GDD.md`. Key facts that shape architecture:
- **4v1 asymmetrical horror**: one Killer, 3-4 Survivors — these are fundamentally different roles (movement, abilities, win conditions), not the same player class with a skin swap. See "Player" below for the current role-split implementation (movement/role-assignment only — no combat yet).
- **Stagger & Finisher (GDD combat design) is currently shelved/stale.** The doc describes a parry-based Stagger Meter + Finisher sequence; the actual implemented combat (see "Combat" below) is a simpler direct system instead — Killer M1 attack downs a Survivor after N hits, an armed Survivor deals much smaller HP damage to the Killer. Parry/Stagger/Finisher may be revisited later, but do not assume it's what's in the code.
- MVP target (GDD, partially superseded by the above): 1 map, 1 Killer with 1 power, 3 Survivors, 2 weapon types (current combat slice has only 1). No progression/cosmetics yet.

## Commands

Unity projects are primarily driven through the Editor GUI, not a CLI build/test pipeline. There is no lint/test command set up yet (no `.asmdef` or test assemblies exist in the project).

- **Open the project**: via Unity Hub, or from the command line:
  `"C:\Program Files\Unity\Hub\Editor\6000.6.0f1\Editor\Unity.exe" -projectPath "D:\Coding Projects\BloodForBlood"`
- **Regenerate network scaffolding**: in the Editor menu, `Blood For Blood > Setup Network Scaffolding` (implemented in `Assets/Editor/NetworkScaffoldSetup.cs`). Safe to re-run: creates the `Ground` plane, `NetworkManager`, and the single `WeaponPickup` scene instance only if missing; always regenerates `Assets/Prefabs/Survivor.prefab` / `Killer.prefab` / `WeaponPickup.prefab` in place (GUIDs/references preserved); (re-)configures the `NetworkManager`'s `ConnectionApproval` and `RoleAssignmentManager` even if a `NetworkManager` already existed from a prior run. **Do not create a `NetworkPrefabsList` asset for anything** — see the Combat/Networking notes below on why.
- **Multi-client local testing**: uses ParrelSync (`com.veriorpies.parrelsync`, installed via git URL, not the Unity Registry). `ParrelSync > Clones Manager` in the Editor menu creates a linked sibling project folder for running a second Editor instance without a full build.
  - **ParrelSync clones symlink `Assets`/`Packages`/`ProjectSettings` with the primary project** — scene/prefab/script changes are shared automatically. Only run `Blood For Blood > Setup Network Scaffolding` in **one** Editor window (the primary). Running it in both is a race: a clone that hasn't yet recompiled the latest scripts can execute a stale cached version of the tool, and two Editor processes independently mutating the same shared scene file can produce duplicate/inconsistent state (this caused the `NetworkPrefabsList` duplicate-registration bug above). The clone will pick up scaffold changes on its own once it regains focus/recompiles.

## Architecture

### Networking model

- Client-server topology (not NGO's distributed-authority mode). `NetworkManager` lives in `Assets/Scenes/SampleScene.unity`, using `UnityTransport` hardcoded to `127.0.0.1:7777` — this is loopback-only for local dev; swapping in Unity Relay/Lobby (or a real server address) is a prerequisite for any non-LAN play.
- **Ownership is deliberately client-authoritative for transforms**, which is a departure from NGO's default. `Unity.Netcode.Components.NetworkTransform` is server-authoritative out of the box; this project uses `Assets/Scripts/Network/OwnerNetworkTransform.cs`, which overrides `OnIsServerAuthoritative()` to return `false` so the owning client drives its own position/rotation. Without this override, only the host's own player would visibly move — non-host clients would have their local movement overwritten every network tick by the stale server-authoritative state. New networked components should default to this same owner-authoritative pattern for anything the local player directly controls (movement, aiming).
- **Gameplay-critical state is server-authoritative** — the deliberate counterpart to the point above, now implemented by the combat system: `SurvivorController.HitsTaken`/`IsDowned`/`HasWeapon` and `KillerController.Health` are all `NetworkVariable<T>` with `WritePermission = Server` (contrast with the owner-written `Stamina`). Server-side methods (`ServerRegisterHit()`, `ServerApplyDamage()`, `ServerGrantWeapon()`) are the only things allowed to mutate them; client input only ever *requests* an action via RPC, never claims an outcome directly.
- **RPC convention**: use the modern `[Rpc(SendTo.X)]` attribute (not legacy `[ServerRpc]`/`[ClientRpc]`, which still work but are being phased out in NGO's own docs). RPC method names must end in `Rpc` (ILPP-enforced at compile time). Any RPC representing "a player acting on their own object" (e.g. `RequestAttackRpc`, `RequestWeaponAttackRpc`) should set `InvokePermission = RpcInvokePermission.Owner` — the default (`Everyone`) lets *any* connected client invoke it on *any* NetworkObject, not just their own.
- `NetworkBootstrapUI.cs` (on the `NetworkManager` GameObject) is a bare-bones `OnGUI` Host/Client/Server button panel for local dev testing only — not shipped UI.
- **Role assignment** (`Assets/Scripts/Network/RoleAssignmentManager.cs`, also on the `NetworkManager` GameObject) uses `NetworkManager.ConnectionApprovalCallback` (requires `NetworkConfig.ConnectionApproval = true`, set by the scaffold script). The host is routed through the same callback as a synthesized approval request, so "first approved connection = Killer, every subsequent one = Survivor" needs no host special-casing. The Killer prefab is selected per-client via `ConnectionApprovalResponse.PlayerPrefabHash` (obtained from `new NetworkPrefab { Prefab = killerPrefab }.SourcePrefabGlobalObjectIdHash` — `NetworkObject.GlobalObjectIdHash` itself is `internal`, this is the supported public route to it); Survivor is the implicit fallback via `NetworkConfig.PlayerPrefab`. **Do not create an explicit `NetworkPrefabsList` asset for these** — NGO auto-registers every `NetworkObject`-bearing prefab into the project-wide `Assets/DefaultNetworkPrefabs.asset` (`IsDefault: true`), which is already auto-wired into every `NetworkManager`. Adding a second list containing the same prefabs causes a hard "duplicate GlobalObjectIdHash" error at `NetworkManager.Awake()` (hit and fixed once already — see git history around the role-system commit). No lobby/cap logic yet — a 5th+ connecting client still gets a Survivor prefab with no rejection.

### Player

- Shared movement lives in the abstract base `Assets/Scripts/Player/NetworkedCharacterMotor.cs` (`CharacterController` + gravity + WASD-via-`Keyboard.current` + facing rotation — the owner-gate and input handling are unchanged from the original scaffold). Role-specific move speed is a `protected abstract float GetCurrentMoveSpeed(bool hasMoveInput, bool sprintHeld)` hook; a server-written `NetworkVariable<PlayerRole> Role` (`Assets/Scripts/Player/PlayerRole.cs`) lets other systems query a player's role network-wide.
- Two more extension points for gating owner-only behavior: `protected virtual bool CanAct => true` (movement input, rotation, and `OnOwnerTick()` are all skipped when false — gravity stays unconditional so a downed player doesn't float) and `protected virtual void OnOwnerTick()` (called once per frame, after movement, only when `CanAct` — this is where each role's M1 input handling lives). Add new owner-driven per-frame behavior here rather than a second `Update()`/input read.
- `Assets/Scripts/Player/SurvivorController.cs`: stamina-gated sprint (`Shift` + moving + `Stamina.Value > 0` → `sprintSpeed`, draining stamina; otherwise `walkSpeed`, regenerating — note `GetCurrentMoveSpeed` is only called while `CanAct`, so stamina doesn't regen while downed; harmless since downed is currently terminal). `Stamina` is owner-written (`NetworkVariableWritePermission.Owner`); `HitsTaken`/`IsDowned`/`HasWeapon` are server-written — see "Combat" below.
  - **Any resource-gated toggle (sprint, a future Killer power/cooldown, etc.) needs hysteresis, not a bare `> 0` check.** A plain `stamina.Value > 0f` gate caused a real bug: the instant stamina hits exactly 0, the sprint condition goes false, so the *regen* branch runs and ticks the value up by a tiny amount — which makes the sprint condition true again next frame, draining it straight back to 0, forever, for as long as the button is held. That's the sprint/walk speed flip-flopping every single frame (60x/sec), which is what surfaced as "jittery, buggy movement." The fix (`staminaExhausted` bool + `minStaminaToResumeSprint` threshold) requires regenerating back up to a real threshold, not just barely above zero, before the resource-gated action can re-engage. Apply the same pattern to any future stamina/cooldown-like mechanic.
- `Assets/Scripts/Player/KillerController.cs`: flat `killerMoveSpeed`, no stamina. Speeds are tuned DBD-style — `killerMoveSpeed` (4) is ~1.15x Survivor's `walkSpeed` (3.5), matching DBD's real killer:survivor base-speed ratio, so the Killer is always a little faster chasing normally; a sprinting Survivor (`sprintSpeed` 5.5) can still briefly outrun them. `Health` is server-written — see "Combat".
- **Camera**: `Assets/Scripts/Camera/ThirdPersonCameraFollow.cs`, a plain `MonoBehaviour` (not networked) added to `Camera.main` and pointed at `transform` from `NetworkedCharacterMotor.OnNetworkSpawn()`, gated on `IsOwner` — each client's own `Camera.main` only ever exists in that client's local process, so this is the correct and complete way to make "only your own camera follows your own character" without any networked camera state. Before this existed, the Main Camera was still sitting wherever Unity's default template placed it — completely static — which is why early testing looked like movement/turning was broken (it wasn't; nothing was tracking the player, so any movement just walked out of a fixed, disconnected view).
  - **Confirmed final model (after several rejected iterations — see below for what was tried and why each was rejected before "fixing" this again):** the camera (`ThirdPersonCameraFollow`) is a **fully independent free-look orbit** — mouse X/Y drive its own `yaw`/`pitch` (pitch clamped `[-20, 60]`) and never directly touch the character's transform. Movement is **camera-relative**: `NetworkedCharacterMotor.Update()` builds `move` from `cameraFollow.FlatForward`/`FlatRight` (the camera's current yaw, flattened) rather than fixed world axes, so `S` always means "backward from whatever I'm currently looking at," consistently, no matter how the camera has been turned. The character's body still auto-turns via `Quaternion.Slerp` to face wherever it's actually moving (unchanged since the first version) — the mouse itself never rotates the character or moves it; it only changes what WASD will mean the *next* time a movement key is pressed. Two other variants were tried and rejected: (1) world-absolute WASD (fixed compass directions) with a fully independent camera — technically satisfies "mouse never affects movement," but since the camera can point anywhere while WASD stays world-fixed, pressing e.g. `S` could visually go sideways/"flip right" depending on which way the camera happened to be facing at that moment; this is what camera-relative movement fixes. (2) mouse directly rotating the character (with movement relative to that) — rejected because using the mouse alone (without pressing any movement key) would still be changing the character's facing, which reads as "the mouse changes my direction," not pure look.
  - **`Mouse.delta` must NOT be multiplied by `Time.deltaTime`** — it's already a per-frame pixel amount, not a rate. Doing so (an earlier bug) makes look speed inversely proportional to framerate — sluggish and inconsistent. Apply `mouseSensitivity` directly to the raw delta.
  - **Cursor lock**: `NetworkedCharacterMotor` sets `Cursor.lockState = CursorLockMode.Locked` / `Cursor.visible = false` once the local player actually spawns (`OnNetworkSpawn`, `IsOwner`) — deliberately *not* at scene load, so the cursor stays free/visible for clicking `NetworkBootstrapUI`'s Host/Client dev buttons beforehand. `Escape` (checked every owner `Update()`, regardless of `CanAct`) toggles lock/visibility, so dev tools stay reachable mid-session.
  - **Careful with the Unity MCP bridge around a live Play session**: forcing a script recompile (`CompilationPipeline.RequestScriptCompilation()`) while the user is independently testing in Play mode (e.g. just clicked Host through `NetworkBootstrapUI`) can collide with `NetworkManager` initialization and throw real exceptions (`ILPPMessageProvider` "Allowed types" mismatch, `NetworkConnectionManager.Shutdown` null refs) — this actually happened once. Before forcing a recompile or otherwise touching the Editor via the MCP bridge, check `EditorApplication.isPlaying` and prefer not to act if the user might be mid-session; it's not just a hygiene nicety, it can produce genuine runtime errors that look like a NGO bug but aren't.
- Prefabs: `Assets/Prefabs/Survivor.prefab` / `Killer.prefab`, same root structure (`CharacterController` + `NetworkObject` + `OwnerNetworkTransform` + role controller + child `Visual`). `Visual` is a real Mixamo humanoid model (`Assets/Art/Characters/SurvivorMale.fbx` / `ZombieGirl.fbx`, imported Humanoid via `Assets/Editor/CharacterModelPostprocessor.cs`, an `AssetPostprocessor` that force-sets `ModelImporterAnimationType.Human` for anything under `Assets/Art/Characters`), not a primitive — `NetworkScaffoldSetup.CreateRolePrefab` falls back to the old primitive-capsule builder (`BuildHumanoidVisual`) only if the model file is missing. Each model needs its own calibration: the two Mixamo downloads import at very different native scales (Survivor ~4.15 units tall, Killer ~2.14 units, measured via the Unity MCP bridge — see "Tooling" below), so `CreateSurvivorPrefab`/`CreateKillerPrefab` apply per-model scale multipliers (0.446 / 0.96) tuned to land both around the CharacterController's ~2-unit height — do not assume one shared scale factor works for a newly added model; measure it first.
  - **No skin/texture on either model** — the Mixamo downloads used "Without Skin", so every material imports as flat white with no diffuse texture. `NetworkScaffoldSetup.AssignCharacterPlaceholderMaterials()` (called first thing in `Setup()`) remaps each FBX's embedded materials (by name, e.g. `Bodymat`, `Topmat`, `ZombieGirl_body_Material`) to standalone flat-color `.mat` assets under `Assets/Art/Characters/Materials/` via `ModelImporter.AddRemap` + `SaveAndReimport` — this is the supported way to override embedded FBX materials persistently (a plain `material.color =` on the embedded material doesn't survive reimport). Looks better than expected in practice because Mixamo's mesh geometry (sculpted face, hair strands, Zombie Girl's decay-patch submesh) does a lot of the visual work even with solid colors. Re-downloading "With Skin" from Mixamo later would give real textures instead — flagged as future work, not done.
- **Animation**: `Assets/Art/Animations/{Idle,Walking,Running}.fbx` are Mixamo motion-only downloads ("Without Skin", small files, no mesh), also force-imported as Humanoid by `CharacterModelPostprocessor` (its path check now also matches `Assets/Art/Animations`). Humanoid retargeting means the same three clips drive both Survivor and Killer regardless of each model's own skeleton proportions. `NetworkScaffoldSetup.CreateOrUpdateCharacterAnimatorController()` builds/updates one shared `Assets/Art/Animations/CharacterAnimator.controller` — a single `Simple1D` Blend Tree on a float parameter `"Speed"` (Idle @ 0, Walking @ 3.5, Running @ 5.5, matching Survivor's `walkSpeed`/`sprintSpeed` — keep these in sync whenever those speed values change) — assigned to every character's `Animator` in `BuildModelVisual`. **`BlendTree.useAutomaticThresholds` defaults to `true`**, which silently normalizes children to evenly-spaced `[0,1]` thresholds and discards whatever you pass to `AddChild` — must be explicitly set `false` before adding children, or real speed values (which are nowhere near the `[0,1]` range) all just clamp to the highest-threshold clip. `NetworkedCharacterMotor.LateUpdate()` (deliberately **not** owner-gated, unlike `Update()`) derives `Speed` every frame from the delta of the already-replicated `transform.position` between frames — this makes it work correctly for observers watching another client's character too, without adding a dedicated `NetworkVariable` just for animation.
  - **Mixamo clip imports default to Loop Time OFF** — without it, a clip plays once then freezes on its last frame (very obvious on the short Running clip, easy to miss on the long Idle clip). `NetworkScaffoldSetup.SetClipLooping()` force-enables `loopTime` on each clip's `ModelImporterClipAnimation` via `importer.clipAnimations` + `SaveAndReimport()` before the Blend Tree is built. Any newly added Mixamo animation clip needs the same treatment or it won't cycle.
  - **`Animator.applyRootMotion` must be `false`** — Mixamo's Walking/Running clips carry root motion (the hip bone's own baked-in forward translation). Left on (the default for a script-added `Animator`), it fights `NetworkedCharacterMotor`'s own `CharacterController.Move()` every frame — both drive the root transform at once, producing erratic jumpy/teleport-like movement and making the follow camera look broken (it's actually just chasing a jittering target correctly). `BuildModelVisual` explicitly sets `animator.applyRootMotion = false` — movement must come from `CharacterController` alone; the Animator only poses bones, never moves the root. Any future character-model setup needs this too.

### UI

- **Survivor HUD** (`Assets/Scripts/UI/SurvivorHudController.cs`): health (from `HitsTaken`/`HitsToDown`) and stamina bars, bottom-left. Built entirely at runtime via code (`Canvas` + `Image` GameObjects, no prefab asset) — same reasoning as `ThirdPersonCameraFollow`: a prefab reference would need an editor-only `AssetDatabase` lookup. Created only for the locally owned Survivor, from `SurvivorController.OnNetworkSpawn()` when `IsOwner` (Killer has no HUD). Bars are driven reactively via `NetworkVariable.OnValueChanged` on `Stamina`/`HitsTaken`, not polled — verified via the Unity MCP bridge by instantiating a Survivor with `Object.Instantiate` in Play mode (plain `PrefabUtility.InstantiatePrefab` in Edit mode does **not** run `Awake()`, so `SurvivorController.stamina` — assigned in `Awake()`, not a field initializer — stays `null`; this is an Edit-mode testing quirk, not a real bug, real gameplay always runs `Awake()` normally on spawn).
  - **`Image.Type.Filled` needs a `Sprite` assigned or it won't visually fill at all.** A code-created `Image` (`new GameObject(..., typeof(Image))`) defaults to `sprite = null`; `Image.Type.Filled`'s fill-mesh geometry is generated from the assigned sprite's rect/UV data, so with no sprite it just renders as a full solid rectangle regardless of `fillAmount` — the underlying value was updating correctly the whole time (confirmed directly via the Unity MCP bridge, `fillAmount` read back as `0.2379407` mid-drain), it just never showed. Fixed by generating a static 1x1 white `Sprite` once and assigning it to every fill `Image` before setting `fillAmount`. Any future runtime-constructed `Image.Type.Filled` bar needs the same treatment — now centralized in `HudBar` (see below), so this shouldn't need rediscovering.
- **Killer HUD** (`Assets/Scripts/UI/KillerHudController.cs`): single health bar (from `KillerController.Health`/`MaxHealth`), bottom-left, same runtime-built approach as the Survivor HUD. Created only for the locally owned Killer, from `KillerController.OnNetworkSpawn()` when `IsOwner` (Survivors don't see it). The background+fill `Image` construction (including the solid-sprite fix above) was factored out into `Assets/Scripts/UI/HudBar.cs` (`HudBar.Create(...)`) once a second HUD needed the identical logic — both `SurvivorHudController` and `KillerHudController` call it now instead of each keeping their own copy.

### Combat

- **Killer M1 attack** (`KillerController`): left-click (`Mouse.current.leftButton`, in `OnOwnerTick()`) fires `RequestAttackRpc` (`[Rpc(SendTo.Server, InvokePermission = RpcInvokePermission.Owner)]`). The server cooldown-checks, then uses `MeleeHitDetector.FindTargets<SurvivorController>(...)` (`Assets/Scripts/Combat/MeleeHitDetector.cs` — a forward `Physics.OverlapSphere` filtered by component type, shared by both attack directions) and calls `survivor.ServerRegisterHit()` on each hit. 3 hits (`hitsToDown`) sets `IsDowned = true`; further hits on an already-downed Survivor are ignored (downed is currently a terminal state — no revive/elimination logic exists yet). Known limitation, not new to this slice: hit detection trusts the server's copy of the attacker's `transform.position`, which is itself owner-authoritative-synced — full server-side movement reconciliation is out of scope.
- **Downed visual**: purely local per-client — `SurvivorController.IsDowned.OnValueChanged` tips the child `Visual` transform (found via `transform.Find("Visual")`) 90° on X. No new `NetworkTransform`; every client computes it identically off the same replicated bool.
- **Weapon pickup** (`Assets/Scripts/Interaction/WeaponPickup.cs`, `Assets/Prefabs/WeaponPickup.prefab`): this is the project's **first in-scene-placed `NetworkObject`** (Survivor/Killer are always dynamically spawned via `RoleAssignmentManager`, never placed in the scene). In-scene placed objects auto-spawn with the scene and don't need `NetworkPrefabsList` registration at all, and their component lifecycle order differs: `Awake → Start → OnNetworkSpawn` (vs. `Awake → OnNetworkSpawn → Start` for dynamically spawned objects like Survivor/Killer). A nearby owning Survivor presses `E`; `RequestPickupRpc` (`[Rpc(SendTo.Server)]`) resolves the *actual* caller server-side via `NetworkManager.ConnectedClients[senderId].PlayerObject` (never trusts a client-supplied reference), re-validates distance, then calls `survivor.ServerGrantWeapon()` and **`NetworkObject.Despawn(false)`** (not a destroying despawn — `OnNetworkDespawn()` is overridden to `gameObject.SetActive(false)` instead, the documented pattern for a permanently-consumed in-scene object). Single-use, one weapon type, no respawn/durability — MVP scope only.
- Armed Survivor's counter-attack (`SurvivorController.OnOwnerTick`, gated on `HasWeapon.Value`) mirrors the Killer's RPC shape (`RequestWeaponAttackRpc` → `MeleeHitDetector` → `killer.ServerApplyDamage(weaponDamage)`), but `weaponDamage` is deliberately much smaller than a full "hit" toward downing a Survivor — the two systems use different units by design (Killer→Survivor is a 3-hit threshold; Survivor→Killer is real HP, `KillerController.Health`, clamped at 0, now feeding `MatchManager` — see "Match flow").
- **Weapon-in-hand visual** (`NetworkedCharacterMotor.AttachSwordToRightHand()`, shared by both roles): parents a placeholder sword (`Assets/Scripts/Visuals/SwordVisualBuilder.cs`) to the model's Humanoid-mapped `HumanBodyBones.RightHand` bone. Purely cosmetic, runs identically on every client (not owner-gated — everyone watching needs to see it). `KillerController` calls it unconditionally in `OnNetworkSpawn` (the Killer's sword is permanent); `SurvivorController` calls it once `HasWeapon` flips true (and immediately on spawn if already true, for a late join after pickup). `SwordVisualBuilder` is runtime code (not under `Assets/Editor`) specifically so both gameplay scripts and the editor-only `NetworkScaffoldSetup.BuildSwordVisual` (the WeaponPickup world model) can share the same geometry instead of duplicating it — a runtime script can't reference `Assets/Editor` code, so the shared piece had to live outside `Editor`.

### Match flow

- **Win/loss** (`Assets/Scripts/Match/MatchManager.cs`, `Assets/Scripts/Match/MatchResult.cs`): this project's **second in-scene-placed `NetworkObject`** (after `WeaponPickup`) — it has to already exist and be listening before any player object connects, so it can't be dynamically spawned like Survivor/Killer. Server-only: subscribes to `NetworkManager.OnClientConnectedCallback`/`OnClientDisconnectCallback`, resolves each connecting client's `PlayerObject` to a `SurvivorController` or `KillerController`, and hooks `IsDowned`/`Health` change events to re-run `CheckWinConditions()`. Also walks `NetworkManager.ConnectedClients` once on its own `OnNetworkSpawn` to pick up the host's player object, which is already connected by the time this in-scene object finishes spawning (the connected-callback alone would miss it). Result: `Killer wins` once every tracked Survivor's `IsDowned` is true; `Survivors win` once `KillerController.Health` hits 0. Written once into a server-authoritative `NetworkVariable<MatchResult> Result` (`None`/`KillerWin`/`SurvivorWin`) — first result sticks, matching "downed is terminal" and "no revive" being out of scope for this slice.
- **`MatchEndBanner`** (`Assets/Scripts/UI/MatchEndBanner.cs`): the one piece of UI in this project that isn't owner-gated — every client (not just the winning/losing side) needs to see the match ended, so `MatchManager` subscribes to `Result.OnValueChanged` unconditionally in `OnNetworkSpawn` (both server and client instances), not behind an `IsServer`/`IsOwner` check like everything else here.
- Scaffold tool creates/places `MatchManager.prefab` the same way as `WeaponPickup.prefab` (`CreateMatchManagerPrefab`/`PlaceMatchManagerInScene` in `NetworkScaffoldSetup.cs`) — no `NetworkPrefabsList` entry, same reasoning as everywhere else.

### Environment / ambiance

- **`NetworkScaffoldSetup.CreateEnvironmentDressing()`**: builds a static, non-networked `EnvironmentDressing` root (skipped if already present, same idempotent-by-name pattern as `Ground`/`WeaponPickup`) containing four perimeter walls (keep players/Killer from walking off the 50x50 `Ground` plane) and scattered obstacle props (rock clusters, dead trees, crate stacks) for DBD-style loopable chase cover — positions chosen to stay clear of the spawn line (`RoleAssignmentManager.SpawnPositionFor`, along X at z=0) and the `WeaponPickup` at `(3,1,5)`. These are plain scene `GameObject`s, not `NetworkObject`s — identical on every client because they're baked into the shared scene file itself (via ParrelSync's symlinked `Assets`), not synced over the network.
- **Collider handling differs from the character/sword builders.** The existing `CreatePart` helper (used for humanoid body parts and swords) deliberately strips the primitive's default `Collider` — a pure visual attached to a character or a hand bone must not physically collide with anything. Obstacle props need the opposite (they should actually block `CharacterController.Move`), so they go through a separate `CreateSolidPart` helper that keeps the default collider. Don't reuse `CreatePart` for future level geometry, or it'll be walk-through by accident.
- **`NetworkScaffoldSetup.SetupAmbiance()`**: dim/cool-toned directional light (searches all scene `Light`s for the first `LightType.Directional`) plus exponential fog (`RenderSettings.fog`) and flat dark ambient light, replacing Unity's bright default lighting for a horror mood. Pure value-assignment, so unlike the object-creation methods above it's naturally idempotent — no "already present" guard, safe to re-run every `Setup()` call.

## Tooling

- **Unity MCP bridge is connected** (Unity's official first-party MCP server, not a community package — ships as part of `com.unity.ai.assistant`, already in `Packages/manifest.json`). When available, prefer it over asking the user to click through the Editor: `Unity_RunCommand` compiles and executes an arbitrary `IRunCommand` C# script directly in the Editor (can call `EditorApplication.ExecuteMenuItem(...)` to trigger `Blood For Blood > Setup Network Scaffolding` without user interaction, inspect live object state, create/destroy temporary objects, etc.); `Unity_GetConsoleLogs` reads the Console directly; `Unity_Camera_Capture` (no args) screenshots whatever the Scene view camera currently frames — pair it with manually setting `SceneView.lastActiveSceneView.pivot`/`.rotation`/`.size` in a `Unity_RunCommand` call first, since `Unity_SceneView_CaptureMultiAngleSceneView`'s `focusObjectIds` expects legacy integer instance IDs and this Unity version's `GameObject.GetInstanceID()` is hard-obsoleted (`GetEntityId()` returns a non-integer `SceneId:LocalId` string that doesn't fit that parameter) — framing the view manually and using `Unity_Camera_Capture` is the reliable path. `Unity_RunCommand` scripts must be `internal class CommandScript : IRunCommand` (exact name, exact accessibility) — see the tool's own template.
  - If the connection isn't live: MCP servers only load at Claude Code session startup, so a `unity-mcp` entry newly added to `~/.claude.json` (written by Unity's Editor-side "Configure" button under Project Settings → AI → Unity MCP) needs `claude --continue` (a fresh process) before its tools appear — mid-session reconnection doesn't pick it up.
  - Requires the project connected to Unity Cloud and an active Unity AI trial/subscription (account/GUI steps only the user can do). Unity's own generative-asset tools (`Unity_AssetGeneration_*`) additionally need a *paid* Unity AI subscription — expect `NoSubscription` warnings in the console from those if not subscribed; harmless, unrelated to project errors.
  - **After editing a project `.cs` file (e.g. via the Edit tool) and before calling `ExecuteMenuItem`/anything that depends on the new code: plain `AssetDatabase.Refresh()` is not reliable.** Editing a script file externally while the Editor never regains OS-level focus (as happens driving everything through the MCP bridge) doesn't reliably trigger a recompile — running the scaffold tool right after can silently execute against the *stale* compiled assembly (confirmed: prefab-regeneration picked up old field defaults twice in a row despite `Refresh()` and `isCompiling` already reading `false`). Force it explicitly: `AssetDatabase.Refresh(ImportAssetOptions.ForceUpdate); UnityEditor.Compilation.CompilationPipeline.RequestScriptCompilation();` (must be **fully qualified** — a bare `using UnityEditor.Compilation;` + `CompilationPipeline` inside the tool's own generated wrapper namespace, which happens to start with `Unity.`, resolves to the wrong type and fails to compile) — then poll `EditorApplication.isCompiling` in a **separate** `Unity_RunCommand` call (it takes a few seconds; the compiling call itself may error with a "could not find type ...RunCommandMacroEvaluatorEntryPoint..." as the domain reload interrupts the tool's own state mid-flight — that's expected, just retry once `isCompiling` reads `false`) before proceeding. Also stop Play mode first (`EditorApplication.isPlaying = false`) — several `Setup()` operations (`MarkSceneDirty`, asset creation) throw `InvalidOperationException` during Play mode.

## Gotchas

- **Active Input Handling is set to "Input System Package (New)" only** (`activeInputHandler: 1` in `ProjectSettings/ProjectSettings.asset`) — the legacy `UnityEngine.Input` API (e.g. `Input.GetAxis`) will throw at runtime. Always use `UnityEngine.InputSystem` APIs.
- Editing scene/prefab files by hand (raw YAML) while the Editor has the project open risks desyncing from the Editor's in-memory state or getting silently overwritten. Prefer adding new script files (safe — Unity hot-compiles these) plus an Editor menu command using Unity's own APIs (`PrefabUtility`, `EditorSceneManager`, etc.) to construct/modify scene and prefab content, following the pattern in `NetworkScaffoldSetup.cs`.
